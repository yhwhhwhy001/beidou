## 2026-09-03 · 第一轮：小时级信号诊断（mainnet 公共数据 2021-06 → 2026-09）

方法：`beidou research diagnose`（按前瞻期计算时序 IC 与横截面 IC，Newey-West t 统计；不做组合构建的等名义信号回测）与 `beidou research validate`（purged walk-forward + CPCV + DSR/PBO + 成本压力）。成本 7 bps 换手 + 实际资金费率。

### 结论

1. **旧系统的 TrendAlpha（5/20/50 小时动量）没有 edge。** 2021-06→2026-09 四币：信号本身毛收益 ≈ 0，1h/4h 前瞻 IC 显著为负（NW t = −6.3 / −3.5），validate 判定 FAIL（OOS Sharpe 0.32，DSR p 0.83，fold 一致性 0.40）。2026-08 的 +2.4% 是上涨月的运气；且旧评估还带着换手率 bug（E-022）。
2. **小时级 1–24h 是反转效应**：tsmom / xsmom / residual 在短前瞻期 IC 全部显著为负；meanrev 在 1h/4h IC 显著为正（t = 6.8 / 3.8）——但 meanrev 的等名义回测亏损（尾部趋势延续时持仓亏大钱），需要时间止损与更强趋势门。
3. **多日/周级横截面效应为正**：
   - flow（taker 主动买卖比，横截面去均值）24–168h 横截面 IC = 0.023–0.056，t ≈ 5–6，是所有信号里最强的预测力；信号本身零成本 Sharpe 0.74，但换手 477 单位 → 需要更长窗口 + 相对再平衡带。
   - tsmom 周级（168/336/720h）：信号本身零成本 +95.7%、Sharpe 0.91；**扣全成本仍 +60.2%、Sharpe 0.66**（成本占比 27%）。首个扣费后为正的候选。
   - xsmom（24/72/168h）零成本 Sharpe 1.09 但成本吃掉 99%；residual 零成本 +120% 但成本吃掉 94% → 都需要更长周期。
4. **换手成本是主要敌人，而且大头来自组合构建而非信号**：逐 bar 波动率缩放让权重每根 bar 微调（tsmom 四币换手 1150 单位 vs 信号翻转 2926 次）。已加入相对再平衡带（同向调仓 < 25% 不动）与新币最短历史过滤（720 根 bar）。
5. carry：横截面 IC 在所有前瞻期显著为正（t ≈ 4–5），但等名义回测亏损——极端资金费率的币（meme）价格波动幅度吞掉排序上的正确性；作为横截面倾斜 + 波动率缩放再评估。

### 下一步

- 对 tsmom（含周级 horizon 集）、flow、xsmom、residual 用完整组合管线 validate；通过者写入 `config/alpha_registry.yaml` 的 evidence 后启用。
- meanrev 加最长持有期与更强趋势门；carry 改为横截面倾斜。
- 实盘：demo 账户 24h 跑通后，用 `beidou report daily` 的按策略归因对照回测预期。

## 2026-09-03 · 第四轮：xsmom / carry 的硬化与否定，以及两处验证工具的诚实性修正

目标是让 xsmom 与 carry 通过验证；方法是先修**经济逻辑上**的缺陷，再诚实验证。结论：**两者作为独立策略都没有通过**，但过程产出了三个可复用的发现和两处工具修正。累计试验数（DSR 分母）：tsmom 45、xsmom 26、flow 28、residual 8、carry 5。

### xsmom

| 第三轮（raw、不跳过、周级） | — | 0.72 | 0.70 / −0.01 | 0.12（4 试验；按累计 26 试验会更差） | 0.05 | FAIL |

机制：**风险调整后的信号与组合层的波动率目标是双重惩罚**——每个币先按自身波动率归一化信号，再按波动率缩放权重，结果是一本几乎等风险、等信心的平书，恰好抹掉了动量最依赖的高波动赢家。这是一条通用教训：信号层与组合层只能有一处做风险归一化。

最终判决来自 3 策略相关性（`research correlate --strategies tsmom,flow,xsmom`）：xsmom 单独 Sharpe 0.70，与 tsmom/flow 相关 0.21/0.26，加入等权组合后 Sharpe **1.80 → 1.66（边际 −0.14）**。即使作为分散化工具也不成立。xsmom 保持禁用，registry 里保留其最佳诚实配置。

carry 唯一说得通的角色是**拥挤度过滤**：tsmom 在某币上做多、而该币的资金费率又处于横截面极端高位时，多头已经拥挤，把信号缩一半。实现为 `tsmom` 的 `crowding_window/cut/penalty` 参数（默认关闭）。对照实验（penalty 0 vs 0.5，其余参数固定）见下一条。

### 两处工具修正（都在结果出来之后才发现，如实记录）

1. **PBO 在网格 <4 时不再作为硬门禁。** CSCV 需要对多个策略排名；只有 2 个配置时 PBO 退化为"两者在多少子区间里互换名次"，0.67 只说明改进量小于子区间噪声，不说明过拟合。改为仅供参考（`min_trials_for_pbo=4`），并在报告中保留数值。
2. **跨轮次试验账本** `reports/research/trials.jsonl`。之前 DSR 只按当轮网格计分母，缩小网格就能"通过"。现在每次 validate 追加每个配置的全样本 Sharpe，下一次自动把同策略的历史试验计入 DSR 分母并用其离散度做方差；账本之前的轮次用 `--prior-trials` 手工申报（上表数字）。

### flow：把负折查清楚

**先修正一个方法论问题。** 报告里的"负折"编号依赖折边界：同一条净值序列在 `min_train` 取 4000/5000/6000 时，负折分别落在第 4 折 / 第 4 折 / 消失（各折 Sharpe [0.63, 1.40, 1.33, −0.61, 2.65] → [0.76, 1.20, 1.16, −0.22, 2.47] → [0.85, 1.74, 0.09, 0.56, 2.12]）。06:27Z 报告的折向量按已知参数无法复现（全样本 Sharpe 1.1582 完全复现，折向量不能——当时的网格未被记录），所以本轮按**日历窗口**定位亏损段，并把这条教训写进工具：折数不是证据，日历窗口才是。

**亏损段 = 2024-10 → 2025-09，亏损几乎全在 2024-11（单月 −8.6%，该折 −9.8%）。** 分解：

| 项 | 数值 |
| --- | --- |
| 多头腿 | +21.2%（Sharpe 1.10） |
| **空头腿** | **−28.0%（Sharpe −1.08）** |
| 最大亏损币 | XRP 空头 −11.0%、ADA −8.9%、SUI −8.5% |

### legacy 的三个模块：只有纪律可移植，没有数值可移植

三份只读审计（tag `v2-governance-final`）的结论，细节见分析文档 E-032 ～ E-035：

- **止盈止损**：交易所原生条件单，止损 = ATR% × 2.0 × 波动率档位 × 点差因子，止盈 = 风险 × RR（2.0 × 9 个手调因子）。没有任何回测证明它有正贡献，且阈值是在错误的 RSI/ATR 数学上校准的（当时的 P0 R-M03-1）。软件侧的 `TrailingExit`（并不从高水位算）与 `TimeExit`（入场时间未持久化，每次重启归零）从未执行。事故统计：仓位无保护时长 p99 1,329s、最大 5,078s。
- **交易池**：5 维打分（点差/深度/成交量/稳定性/容量）+ 24h 观察期 + 隔离状态机，三套互不一致的实现；成交量分恒为 0 导致**任何币都无法激活**；隔离 = 冻结，被隔离币的仓位既收不到入场也收不到退出信号。时点快照机器从未接进回测。
- **自适应 sizing**："canonical" 引擎是可用保证金比例 × 八个标量之积，从未验证（回撤输入硬编码 0；唯一一次 soak 因 MIN_NOTIONAL 在 3 秒内零成交死亡）；实际交易路径 1% × 2% 双重叠加 → 名义恒 ≈ 10 USDT；交易所杠杆从未同步（模型按 3x 算，交易所停在 20x）。

移植的纪律：缺特征就不交易而不是编默认值；min-notional 拒绝而不放大 + ROUND_DOWN；退出侧遍历仓位而不遍历池子；只有交易所的 ACK 才算数；一个风险预算。

## 判定规则修订（D-020，2026-09-04；先登记，后执行）

**背景。** 第六轮发现 tsmom 的 registry 配置（拥挤度关闭）与其证据（拥挤度 0.5 的 133239Z）不一致；随后的三次重验（时点 16 点网格、时点两点对照、静态 16 点网格）除 DSR 外全部通过，DSR p 分别为 0.40 / 0.32 / 0.33。原因不在策略，在尺子：133239Z 的 p 0.0002 来自账本里只有近似相同配置时接近 0 的合并方差；今天账本里 40 条 tsmom 试验混入了旧的小时级 horizon（Sharpe ≈ 0），合并方差把 50 次试验的零假设最大 Sharpe 抬到约 1.5，全样本 1.64～1.72 的候选永远不"显著"。DSR 在两个方向上都失真了。

**操作者决定（2026-09-04，对应五个选项中的第 4 项）。** 判定改为以样本外为主，对所有策略统一，先写入本段再改代码：

| 项 | 规则 |
| --- | --- |
| PASS | 走前 OOS Sharpe ≥ 1.0 **且** OOS 净收益序列的 Newey-West t ≥ 2.0 |
| WEAK_PASS | OOS Sharpe ≥ 0.5 且 t ≥ 1.5 |
| 硬门（任一不满足即 FAIL） | 折一致性 ≥ 0.6；CPCV 负路径比例 ≤ 10%；PBO ≤ 0.30（网格 ≥ 4 时）；成本 2× Sharpe ≥ 0 |
| DSR | 每份报告照常输出（合并方差；第七轮将并列输出家族方差口径），**不再一票否决** |

理由：DSR 惩罚的是**样本内** Sharpe 的选择偏差；走前验证已经把参数选择放在训练段里做，OOS 序列的显著性是更干净的检验。跨轮的"家族选择"（试过哪些网格、哪些救援）仍由账本计数暴露，并配合预登记与探针书（D-019）控制。t 统计量用 HAC 方差（`metrics.newey_west_tstat`），对小时级收益的自相关与波动率聚集做了修正；5 年 OOS 下 t ≥ 2 大致等价于 OOS Sharpe ≥ 0.9，样本更短时要求更高。

**规则的两处局限（第七轮会话提出，本会话独立复算证实；`scratchpad/verify_d020.py`）。**

1. **两个 PASS 条件在长窗口上并不独立。** 小时级净收益几乎无自相关，HAC 修正只有 0.1%～0.4%：181803Z 上 t = 3.5027 而 Sharpe × √年数 = 3.5005（比值 1.0006），拥挤度关闭臂 3.7333 对 3.7282。因此 t ≥ 2 在 5.14 年窗口上等价于 Sharpe ≥ 0.88，**比并列的 Sharpe ≥ 1.0 更松**；t 门只在 OOS 窗口短于 4 年时才真正起作用（t = 2 与 S = 1 在 4.0 年处相等）。这不改变 tsmom 的判定（1.54 / 3.50 两项都远超），但不能把 D-020 说成"两个独立条件"——它是一个 Sharpe 门加一个**短样本保护**。下一轮需要补一个真正对选择敏感的条件（按 horizon 家族分组的 DSR，或最差折 Sharpe 下限）。
2. **报告头条的 OOS 是"逐折择优"的混合口径。** 181803Z 每折选中的 `crowding_window` 是 [72, 0, 72, 72, 0]，其中三折跑的是 registry **不运行**的拥挤度修正。独立复算：registry 实际配置（拥挤度关闭）单独的走前 OOS Sharpe **1.6450**、t **3.7333**、各折 [1.47, 0.49, 2.24, 1.71, 2.31] 全正；开启臂 1.5291 / 3.4798；混合 1.5445 / 3.5027。方向是保守的（实际运行的臂更好），`best_params` 也仍等于 registry 参数，所以证据门有效；但读报告时不要把 1.54 当成实盘配置的成绩。

**对现有 registry 的影响。** tsmom 用"拥挤度关闭 vs 开启"的两点对照（与 175236Z 同一实验，registry 参数 `crowding_window: 0` 即对照臂）在时点 universe 上重验，按新规则判定后更新证据指针；flow 只做空本轮**不**重验，仍以探针书身份运行（它在新规则下也可能达到 t ≥ 2，但它的跨轮选择次数最多，样本外证据只能由实盘产生）。实现：`beidou_alpha/validation/walk_forward.py`（`oos_t_stat` / `oos_t_lags` / `oos_bars`）、`beidou_alpha/validation/verdict.py`。

### 第六轮补充（round 6b，2026-09-04）：把 KILL-027 的机制关掉，并给实盘装上可复现性监控

第六轮修的是 KILL-027 的**实例**（拥挤度修正被静默跳过）；本次修的是**机制**——让"实盘跑了没被验证的配置"这件事无法再悄悄发生。

- **信号声明自己的输入需求。** `SignalSpec.needs_funding(params)`：tsmom 只在拥挤度修正真正打开时（window > 0 且 penalty > 0）声明，carry 恒为真。声明为真而没拿到资金费率历史时，`AlphaModel.targets` 直接报错；行情端口不提供 `funding_history` 时 `LiveEngine.startup` 拒绝启动。也就是说，把 `crowding_window` 改回 72 现在要么正确运行、要么明确失败，不会再有第三种结果。
- **实盘面板 == 研究面板。** 新增 `MarketData.funding_history(symbols, start_ms)`，取与 K 线同一窗口的结算费率，由 `Panel.from_frames` 按 bar 对齐——与研究侧 `load_panel` 完全相同的语义。测试直接断言：拥挤度打开的配置下，实盘路径与研究路径的逐策略目标**逐位相等**，且该 panel 上修正确实在起作用（否则这个相等没有意义）。
- **一个地方构造周期输入。** `beidou_live/inputs.py` 被引擎和验证器共用，离线复现不会与它所复现的周期发生实现漂移。资金费率历史只在模型需要时才取（额外请求数为 0，除非有信号声明）。
- **M-011 `beidou live verify`。** 用公共数据 + `state.json` 离线重算上一周期的 contributions 并逐币比对。contributions 必须相等；targets 的差异只是提示（退出层 / 节流 / 护栏在模型之后动作）。**对运行中的循环实测（bar 2026-09-04T01:00Z）：tsmom 与 flow_short 两本书的最大差异均为 0.0**，1,442 根 bar、15 个币。这是第一条"实盘输出可被独立复现"的证据。

## 2026-09-04 · 第七轮补充：H-001（`conviction_mode: sign`）按预登记规则执行

三条检查全部通过 → 规则判 **ADOPT**。但把"通过"当成"更好"是不诚实的，配对检验说得更清楚：

- 两条净值 OOS 相关 **0.966**；逐 bar 收益差的 Newey-West **t = −0.047，p = 0.963**。年化收益差 −0.0009。**幅度不携带任何收益信息**，这是本节真正的结论，比 Sharpe 的 −0.04 更值得记住。

- 那为什么收益相同、成本更低，Sharpe 却略低？因为 `sign` 把每个可执行仓位放到满仓，平均敞口从 0.383 升到 0.445，波动率目标之后仍留下略高的实现波动。它买到的是更低的换手与更浅的回撤，付出的是略粗的仓位粒度。

**两个操作性发现（本节的副产品）：**

1. `research validate` 的 `best_params` 按**全样本 Sharpe**选，所以一个按预登记规则胜出、但全样本 Sharpe 略低的候选永远不会成为网格报告的 `best_params`。配合已上线的"registry 参数必须等于报告 `best_params`"启动门（D-023），采用这类候选**必须**另出一份单配置报告——这正是 020459Z 的用途。若以后这种情况变多，应让 `validate` 支持按预登记规则而不是全样本 Sharpe 选 best。

## 判定规则补门（D-028，2026-09-04；先登记，后实现，后评估）

KILL-045 指出 D-020 的两个 PASS 条件不独立：小时级净收益上 NW t 与 `Sharpe × √年数` 的比值是 1.001，所以在五年窗口上 `t ≥ 2.0` 等价于 `Sharpe ≥ 0.88`，比并列的 `Sharpe ≥ 1.0` 更松。D-020 因此实际只有一道门，而且**没有任何条件对「这个策略跨轮次被试过多少个配置」敏感**——走前 OOS 只内嵌了折内选择。

### KILL-042 解释清楚了：负的时序 IC 是重叠标签的伪象，而幅度确实无信息

第一轮记录 tsmom 的时序 IC 在各前瞻期为 −0.12 ～ −0.27，与策略赚钱矛盾，两轮都写着「下一轮复核」而没有工具。现在有了（`sign_bucketed_ic`，接入 `research diagnose`）：非重叠采样（每 h 根取一根，D-011），按分数符号分桶。

| 前瞻 | 重叠口径时序 IC | **非重叠 IC** | 多头桶 n / 桶内 IC / 平均前瞻收益 | 空头桶 n / 桶内 IC / 平均前瞻收益 |
| --- | --- | --- | --- | --- |
| 24h | −0.081 | **−0.01** | 11,278 / −0.03 / **+0.253%** | 14,538 / −0.03 / **−0.073%** |
| 72h | −0.106 | **+0.01** | 3,749 / −0.02 / **+0.777%** | 4,832 / −0.05 / **−0.307%** |
| 168h | −0.135 | **+0.03** | 1,587 / −0.02 / **+1.788%** | 2,075 / −0.06 / **−1.027%** |
| 336h | −0.218 | **−0.01** | 788 / −0.09 / **+0.885%** | 1,038 / −0.06 / +0.091% |
| 720h | −0.214 | **+0.05** | 350 / +0.03 / **+3.401%** | 479 / +0.07 / **−2.902%** |

三条结论：

1. **强负的时序 IC 是重叠标签造成的**，换成非重叠采样后它消失（−0.01 ～ +0.05）。这正是 D-011 存在的理由，只是从没有人把它用在时序 IC 上。

## 2026-09-04 · D-030：归因窗口用的是宿主时钟，而 income 的 startTime/endTime 不受 -1021 自愈保护

**但那一轮没有写出归因行，而原因不是平仓。** 签名请求对错误的宿主时钟是免疫的——`-1021` 会让 REST 客户端 resync 再重试，所以 `timestamp` 永远是场地时间；而 `/fapi/v1/income` 的 `startTime`/`endTime` 是普通查询参数，一直是从 `self.clock.now_ms()` 原样传过去的。宿主慢 1 小时，于是循环每次都在问一个一小时前的窗口。直接测到：96 行、净 +23.98 USDT 的 income 停在场地时间 07:51–07:53，而循环正在查询 `[06:53, 06:58]`，什么也没取到。

**收入没有丢，是迟到一小时**，并且被归到一小时之后那一轮的 `last_contributions` 上。对 M-010 来说这正是不能容忍的那一种污染——KILL-006 决定不做历史留出，理由就是"实盘归因是唯一干净的样本外"，那条通道本身有一小时的错位。

修法：`venue_time_ms()` 直接读 `-1021` 路径已经在维护的 offset，`startup` 显式 `sync_clock()` 一次（不再等第一次拒绝去发现——那里 offset 为 0 不会报错，只会安静地少一小时归因）。水位线不动，因此修完的第一轮是一个更宽的窗口，把缺口补回来；此后是场地基准、首尾相接。没有场地时钟的 venue（paper、fake）回落到宿主时钟，时钟抛异常也不会让一轮失败。

重启后实测：窗口 `[07:00:08 → 08:04:19]`（场地时钟），一次取回 15 个标的、`REALIZED_PNL +26.2986`、`COMMISSION −2.3184`、`FUNDING −0.1753`，`unattributed 0.0`。

## 2026-09-04 · P12：把历史系统的"盘口质量筛选"换成可回测的流动性代理（预登记，先写后跑）

### 起因：一次与历史系统的逐模块对比

操作者要求把当前系统与 `v2-governance-final`（治理期，10.0 万行包代码 + 10.2 万行测试，当前系统是 1.14 万 + 0.55 万）做模块对比，并从"活跃交易池"开始。对比结果先说清楚，因为它决定了本次要问什么：

**当前系统并不缺这个模块。** `beidou_data/pool.py` 的 `LivePool` 每个 UTC 日重排一次，`point_in_time_membership` 为研究侧重建同一规则的时点成员表，`beidou_live/engine.py` 已接线并在跑。历史系统里有**三份**交易池实现，其中两份（`trading_pool.py` 的 `TradingPoolManager`、`universe_hysteresis.py` 的 `UniverseHysteresis`）**没有任何生产调用方**，只被测试引用——在 100% 覆盖率门禁下，死代码也要被测到。

真正接线的是 `trading_pool_lifecycle.py`（650 行）挂在 `beidou_core/engine.py`（15,268 行）上：OBSERVING → PROMOTED → ACTIVE → QUARANTINED，五维打分（点差 0.25 / 深度 0.25 / 成交量 0.20 / 稳定性 0.15 / 容量 0.15）。它比当前系统多出来的东西是**盘口质量**这一维。但照抄它是错的，有两个具体理由：

1. **五维里有两维是占位符。** `stability_score` 取 0.5，若 kline features 字典里有 close/high/low 三个 key 则取 0.8——它度量的是"字典有没有字段"；`capacity_score = 1 − 年化波动率`，与容量无关。两者合计权重 0.30。
2. **它没有回测对应物。** 成员资格是实时 WS/REST 打分的产物，落在 SQLite 的 `trading_pool_events` 表里。回测无法复现"当时哪些币是 ACTIVE"，因此任何用它做的历史验证都带幸存者偏差。当前系统整条证据链（D-013）恰恰建立在这个属性上——这是不能拿去换的那一样东西。

所以本次不移植，改问一个**两侧都能算**的问题。

### 为什么是 Amihud：因为盘口数据不存在

研究仓里只有 K 线，没有任何历史盘口深度与点差，将来也补不回来（币安不发布历史 orderbook 归档）。因此"点差/深度筛选"在这套系统里**永远无法按 D-013 在时点 universe 上验证**，硬上就等于拿实盘当留出期烧，而那 6 个月留出已经被 97 个配置看过（KILL-006）。

Amihud 非流动性 `ILLIQ = mean(|日收益| / 日成交额)` 只需要日线，研究侧与实盘侧都算得出，因此可以按 D-013 用同一条规则进两侧。它测的是价格冲击，与点差/深度是同一族的东西，不是同一个东西——这一点写在前面，不打算在结果出来后再补。

### 先验（写在结果之前）：这条筛选很可能是惰性的

池子已经是全场成交额前 15 的 USDT 永续，而 Amihud 的分母正是成交额。**最可能的结果是它筛不掉任何东西。** 这不是失败，是一个结论：它会把"历史系统有而我们没有的那一维到底值不值钱"这个问题从猜测变成读数。我预期第 0 段就停在这里。

### 两段式，第 0 段不消耗试验账本

**第 0 段：约束力测量（不跑回测、不写账本）。** 在现有时点成员表的候选集上算 30 天 Amihud，测两件事：

- (a) 这条筛选会改变多少比例的 **symbol-refresh**；
- (b) 同一次刷新的成员之间 `log(ILLIQ)` 的四分位距——有没有可排序的离散度。

**停止规则（预登记）**：若 (a) **< 3%**，判定为惰性，**不跑回测、不写账本**，把 (a)(b) 两个读数写进日志然后停。3% 这个线不是随手定的：成员表现已是**日刷新 2042 次、平均 17.58 个成员**（2021-01-31 → 2026-09-03，并集 211 个币），约 35,900 个 symbol-refresh，3% ≈ 1,080 个。低于这个量级，被改动的账面时间不足以产生账本噪声零假设能分辨的差异（P10 那次能判定的差异是 +0.142 Sharpe，5–95% 区间 [+0.064, +0.218]），跑出来的任何数字都只是噪声。

**第 1 段：只有第 0 段过线才跑，每个配置一条账本记录。**

- 规则形式：候选币的 30 天 ILLIQ **> m × 候选集中位数** 时排除。
- 窗口**固定**为 `volume_lookback_days = 30`，不作自由参数（防止网格膨胀）。
- 网格：**m ∈ {2, 4, 8}**，共 3 个配置，跑之前定死，不在看到结果后加档。
- 两侧同一条规则：`point_in_time_membership` 与 `LivePool.select` 都用它，否则就是又一个 D-013 不对称——今天刚修完两个（见本轮 P0）。

### 判定规则（预登记）

- 主判定按 **D-020**：时点 universe 的走前 OOS 为准。
- **PASS 需要三条同时成立**：OOS Sharpe ≥ 基线 + 0.05；OOS 最大回撤恶化 ≤ 1pp；并且按 **D-028**，OOS Sharpe ≥ 该策略账本去重后配置数下的期望最大值。
- **机制检验，方向与 P10 相反。** 这条筛选宣称的机制是"流动性差的名字，真实交易成本高于成本模型的假设"。因此把同一组权重**按零成本重新定价**后，Sharpe 增益**必须至少消失一半**。若增益在零成本下依然存在，那它就不是在省成本、而是在选名字——那是不会外推的选择效应，**无论 Sharpe 多好都判 REJECT**。（P10 那次是反过来用同一把尺子：+0.142 里只有 9% 来自省下的换手成本，因此判定它是持仓时序的改变而不是效率节省。同一个工具，这次要求相反的答案。）
- 静态 universe 作稳健性腿，不要求通过；若两侧方向相反，要在日志里解释，不得忽略。

### 账本记账：一个必须手工补的坑

试验记录的去重签名是 `(param_key, range_start, range_end, symbol_count)`——**是符号个数，不是符号集合**（`beidou_alpha/validation/ledger.py:46`）。这条筛选改的是成员资格，`param_key` 一个字都不变；只要面板的符号并集大小不变，三档阈值会被去重成**一条**，账本就会把 3 次尝试记成 1 次，系统性低估选择压力。

因此三次运行都要用 `--prior-trials` 手工申报补差：**基线 1 + 三档 3 = 4 次实际尝试，账本自动计入 1 条，手工申报 3。** 数字写在跑之前。这个坑本身也记在这里，因为它对**任何**改变成员资格而不改变策略参数的实验都成立，不只是本次。

## 2026-09-04 · P13：风险预算显式化（`vol_target` 0.15 → 0.30），以及为它先补上的两个休眠护栏

分析文档：本轮走 deep-analysis L 级，**Weak GO**。起因是操作者报告三个实盘异常（长时间不下单、杠杆显示 20x、下单量很少）。前两个已由并行会话结掉（`f5b7546`/`e5617dd`）；本节处理剩下的两项——「自适应杠杆」与「下单量」——结论都与提问的形式不同。

### 一、「自适应杠杆」：KILL，因为它没有目标函数

不是做不到，是**没有可优化的量**。三条 E1 证据指向同一处：

- 仓位由 `target_weight × equity` 决定，杠杆不在其中；
- `/fapi/v1/leverageBracket` 的 `maintMarginRatio` 按**名义档位**索引（BTCUSDT 首档 `notionalFloor 0 / notionalCap 50000 / maintMarginRatio 0.004`），与所选杠杆无关，币安官方文档同述；全仓强平由维持保证金决定，因此杠杆不进入风险方程；
- 保证金：L≥3 时对 gross ≤ 2.0 从不绑定（实测 06:53 那一轮 budget 9,672 vs needed 532）。只有 L≤2 才会把加仓单缩到 0。

D-016 当初的记录（「敞口不变」）本来就说明了这一点。第五轮审计对 legacy 的判词也在同一处：*自适应 sizing 是八个标量之积、从未验证、交易所杠杆从未同步*。**重设计就是把那条路再走一遍**，因此 KILL。

一并撤回我自己在排查中提的一个方向：「让 `derive_leverage` 按实际 gross 而不是 `max_gross` 推导」。它是错的——实际 gross 0.256 会推出 L=1，而 L=1 时 gross 2.0 的预算为 0，整本书会被锁死。按最坏情况取值是**正确设计**。

**真实缺陷在别处，已修（M3）。** `derive_leverage` 的 `max_leverage` 截断会静默破坏它自己的 `margin_cap` 不变量：`max_gross 3.0 / margin_cap 0.40 / max_leverage 5` → 实得 5x → 初始保证金 60%，无告警。今天不可达只是因为 `2.0 = 5 × 0.40` 恰好相等。启动时校验，`auto` 模式下不满足即拒绝启动；`fixed` 模式豁免，因为那里 `margin_cap` 根本不参与（profile 自己的注释「was 100% at a fixed 2x」就是那个状态）。

### 二、「下单量少」：症状是 demo 余额，真问题是风险预算从未被声明

单笔名义 = `w × equity`，随权益线性放大，真实资金规模下自动消失。**唯一不随规模消失**的是 `|w| < no_trade_band` 的死币（`w·E < 0.005·E ⟺ w < 0.005`，与 E 无关）——那是带的问题，不是 sizing 的问题。

真问题是：`vol_target: 0.15` 是 `PortfolioParams` 的默认值，不在任何 D-决策、预登记或试验账本里。操作者本轮声明最大回撤预算 **50%**，而当前构造运行在约 12% 的预算上，错配约 4 倍。

**它不含 alpha，这是量出来的**：把权重乘以任意 k 重新定价，净 Sharpe 在 k ∈ {1, 1.5, 2, 2.5, 3, 4, 5} 上**精确不变**（时点 1.6972、静态 1.5760）。必须说清这条恒等式的性质——它是回测的**算术性质**（毛 P&L、换手成本、资金费三项全部线性于权重），不是关于世界的发现。成本模型对任何下单量都收固定 7 bps，`max_participation` 根本不在回测里。在 demo 名义（单笔 40–800 USDT）下这是好近似；**真实资金前必须在含冲击的成本模型下重新推导 k**，这一条记为「范围之外」，不是「已完成」。

**取值规则先写后跑**：取自助 q95 回撤仍在声明预算内的最大 k，**两个 universe 都要满足**。周块自助（168h 块、2,000 次重抽、种子 20260904，`scratchpad/vol_target_drawdown_bootstrap.py`）：

操作者报告「所有订单都是 5 倍杠杆，应该按每个交易对的市场情况设定」。四条 E1 证据：

- `derive_leverage(2.0, 0.40, 5, bracket)` = `ceil(2.0 / 0.40)` = **5**，而 `max_leverage` 根本不绑定——抬到 10 / 20 / 125 输出都还是 5。主流永续档位上限 20–125，因此 15 个币全部落 5，`state.json` 实测 `Counter({5: 15})`。只有档位上限 < 5 的币才会更低（bracket 4 → 4，3 → 3）。
- `contributions.tsmom` 是**纯符号 ±1**，15 个币无一例外。因此权重从 0.0056（AKEUSDT）到 0.0703（BNBUSDT）这 **12.5 倍**的差异，100% 来自组合层的逆波动率定价，没有任何一份来自信号强弱。
- 用仓库自己的 `ewm_vol` 复算最新一轮：`|w| ÷ (vol_target/σ)` 在 σ 从 79% 到 963% 的 **12 倍跨度**上稳定在 0.12–0.20。残差来自协方差 scalar 与无交易带的路径依赖，不是别的机制。
- 保证金实测 9.8%，对 40% 的 `margin_cap` 有约 18 倍余量；杠杆此刻不绑定任何东西。

外加一条与实现无关的场地事实：**币安 USDM 的杠杆是交易对/账户级设置，不是订单参数**，「每一个订单的杠杆」在 API 层面不存在。

D-037 已经把这件事判过一次（2026-09-04，P13 第一节 KILL）。本轮没有任何新证据，因此按 C.7 规则 2 不重开——操作者这次看到的「全是 5x」恰恰是 D-037 之后的**正确行为**，而上一轮看到的「20x」是 legacy 残留。

### 二、真实缺陷：一个没有仪器陈述的正确事实

值得记下的不是结论，是**它为什么会被问第三次**。D-037 的论证完整、证据是 E1、结论正确——然后写在 `ARCHITECTURE.md` 里。日报只印 `last_targets`，没有任何可以对照读的量，于是全系统唯一可见的每标的数字就是交易所那个统一的 5x。**正确但无人陈述的事实，和未经证明的断言，在操作者那里长得一模一样**，这正是 `test_source_budget.py` 那一页存在的理由。

M-015 因此写成证伪器而不是展示：

```
vol_spread  = max σ / min σ            市场有多不一样
risk_spread = max |w|σ / min |w|σ      它们的风险贡献有多不一样
compression = risk_spread / vol_spread
```

实盘 2026-09-05 读 **0.13**——12.2x 的市场波动离散度被压成 1.6x 的风险离散度，stage 1 吸收掉 87%。**删掉 stage 1 它收敛到 1.00**（权重不再依赖 σ，两个离散度相等，测试里就是这么验的）。0.50 的界放在 0.13 与 1.00 之间，是宽界不是推导阈值，理由写在函数里：无交易带会攥着陈旧权重而 σ 在其下漂移、`max_weight` 会在最平静的名字上绑定、带幅度的信号会把 conviction 放回分子。

**一个具体的取舍**：`asset_vol` 从 `portfolio.py` 提取为具名函数，并经 `TargetWeights` 随每轮落盘，而不是让日报去行情档案里重算 σ。后者更短，而且答的是另一个问题——另一根 bar，且与构造实际用的半衰期没有任何绑定。测试里那条恒等式（`w × σ` 跨币恒等于 `vol_target × scalar`）就是防这条捷径的。

一并纠正：本节的指标最初写成 M-011，而 M-011 是 `beidou live verify` 的编号，已改为 M-015。

## 2026-09-05 · D-040：清单对资金费归档是瞎的——修的是布局被写了两遍，不是那一行判断

起点是一个答不上来的问题：2026-09-04 那次 `research mine` 到底有没有计入资金费。清单本该回答它，结果发现清单在这一格上是瞎的。「发现」与「推断撤回」那一半由并行会话记在同日的挖矿提案者分析里（E-010），此处不重复；**本条是修复与处置**，其中处置那一半——已经落盘的报告该怎么算——是这次真正需要决定的东西。

### 一、缺陷：布局在两个模块里各写了一遍，然后分了岔

`beidou_data/manifest.py` 的 `_store_fact` 用一套走法伺候两个 store：`for child in ...: if not child.is_dir(): continue`，然后取 `child/<interval>.parquet` 或 `child/funding.parquet`。**这是 klines 的布局**（`klines/<SYMBOL>/1h.parquet`）。资金费的实际布局是 `store.py` 的 `funding/<SYMBOL>.parquet`——平铺，一符号一文件。于是 `is_dir()` 对每一个资金费文件都为假，全部跳过。

盘上 231 个文件 / 20,196,970 字节，修复前 `build_manifest` 读到：

```
klines : {'symbols': 231, 'bytes': 444306711, 'fingerprint': 'fb9391ce34395763'}
funding: {'symbols': 0,   'bytes': 0,         'fingerprint': '44136fa355b3678a'}   ← 经核即 _digest({})
```

后果不是「少记一个字段」，而是**`manifest_problems` 对资金费归档永远不会告警**：记录侧与当前侧恒等于同一个零，两边永远相等。D-034 把 1,010,914 条结算里的 441,678 条从静默填零改成正确对齐，重写了那份归档的含义，而没有任何一份报告的清单能看见这件事。KILL-027 / D-038 的同一个形状——一个声称自己是某个量、实际不是的数字，且没有仪器能看见——低了一层。

### 二、修法：布局只留一份，让清单去问 store

按「分支处理平铺布局」修（`if interval is None`）能让数字对，但**会把导致这次事故的重复原封不动留在原地**。所以改成让 store 自己交出路径：新增 `FundingStore.symbols()` 与两个 store 的 `directory` 属性，`_store_fact(directory, paths)` 只接收已解析好的路径。`manifest.py` 现在一个字的布局知识都没有。测试夹具同样经由真 store 写文件——夹具里手写一遍布局，就是这次事故本身的第三次重演。

复核（真实数据根）：`funding` 231 符号 / 20,196,970 字节 / 指纹 `08ada6f733c09ee1`；**`klines` 三个字段逐位不变**（`231 / 444306711 / fb9391ce34395763`），所以历史报告的 klines 侧仍然可比，这次修复没有顺手作废别的东西。

### 三、处置已落盘的报告：v1 的零读作「没测过」，不是「归档是空的」

先量再决定。全仓 `reports/` 里**带 dataset 清单的报告只有 4 份**，全部是 2026-09-04 的，全部带着瞎掉的资金费事实。修复前跑一遍 `manifest_problems`：其中 3 份**本来就已经在告警**（universe.selected_at_ms 与 klines 229→231），只有 `tsmom-validation-20260904T193707Z.json` 一份是干净的。所以「修完会淹掉一片告警」这个担心量出来是 **1 份报告从干净变成不干净**，不是洪水。

三个选项，取第三个：

1. **照常报成漂移**——会输出 `funding.symbols: 0 -> 231`，即断言「归档从无到有长出来了」。**这是对历史的假陈述**：归档一直在，瞎的是仪器。而且这种行文会训练读者忽略 funding 那一行。
2. **静默压掉**——把「不知道」塌缩成「一致」。本模块唯一明确拒绝的就是这件事，`test_a_result_with_no_manifest_reports_unknown_provenance_not_agreement` 就是为它写的。
3. **报成「未记录」**（采纳）——说真话：那份报告的资金费出处从未被记录过，无法核对。

v1 的零本来就是**真歧义**：`{0, 0, _digest({})}` 既可能是 231 个文件也可能是空目录，记录里没有任何东西能分辨——所以「未知」是它的准确读数，不是权宜。（`funding: null` 不在此列，仍然可信：目录确实不存在，那一点 v1 看得见。）

为了不让这个歧义变成永久性的，清单加 `MANIFEST_VERSION = 2` 印戳：**v1 的零不可读，v2 的零是一次测量**。没有印戳的话，为了对旧报告诚实，将来每一个真正空的归档都得被叫作「未知」。印戳落在 `MANIFEST_FIELDS` 之外，**不移动任何既有 digest**。

修复后那 4 份的输出：3 份原有的 klines/universe 漂移行一字不变，各自多一行「funding provenance was never recorded」；第 4 份只多那一行。

`beidou_data` +55 行，ceiling 1258 → 1313，第二十次抬升，理由句写在 `test_source_budget.py` 里。行数不在那个一字修复上，在「布局只存一份」和版本印戳上。

测试：`tests/data/test_manifest.py` 5 → 9 条，两条新的先红后绿（其中一条红在 `assert []`——整份资金费归档被加进去而 `manifest_problems` 一声不吭，这才是缺陷在它真正要害处的样子）。全套 342 passed，ruff / mypy 干净。

## 2026-09-06 · E-040 的另一半：研究路径也在跑没有输入的信号——连着五轮，后四轮修的都是前一轮的修复
