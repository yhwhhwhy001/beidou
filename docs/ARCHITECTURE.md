# 北斗 V5 架构

```
mainnet public data ──► beidou_data ──► beidou_alpha (features → signals → ensemble → books → portfolio → overlays) ──► target weights
        │                    │                                                                                       │
        │              pool (daily refresh / point-in-time membership)                                                │
demo venue (Binance USDⓈ-M) ◄── beidou_exchange ◄── beidou_live (scheduler → throttle → exits → guards → rebalancer → margin → execution → reconciler → reports)
```

| 包 | 职责 | 允许依赖 |
| --- | --- | --- |
| `beidou_shared` | 值类型（Side、InstrumentRules、Position、OrderRequest/Ack）、YAML/env 配置加载 | stdlib、pyyaml |
| `beidou_data` | 官方月度归档下载与校验、REST 补齐、parquet 存储、universe 排名滞回、**交易池**（`pool.py`：日线同步、时点成员表、实盘每日刷新）、实盘闭合 K 线 | shared |
| `beidou_alpha` | 特征、信号、集成、组合构建、**overlays**（退出层、回撤节流）、回测、验证、报告。**纯函数，零 I/O** | numpy、pandas |
| `beidou_exchange` | Binance USDⓈ-M REST：签名、限频、熔断、规则量化、下单/查单/仓位、杠杆档位；host allowlist + kill-switch | shared、httpx |
| `beidou_live` | bar 驱动循环：目标权重 → 节流 → 退出层 → 护栏 → 与真实仓位求差 → 参与率/保证金缩放 → 幂等下单 → 对账 → 归因/心跳/日报（含 P13 风险预算监控）；每日池刷新与显式平仓 | alpha、data、exchange、shared |
| `beidou_cli` | `beidou data sync|pool|status`、`research backtest|validate|diagnose|correlate|overlay`、`live run|status|flatten|kill-switch`、`report daily` | 全部 |

唯一的架构测试：`tests/architecture/test_import_rules.py`（依赖方向 + import 时无副作用）。

## 关键设计决策

- **D-002** 研究与信号只用 mainnet 公共数据；执行在 demo。demo 成交量是合成的、价格有偏差。
- **D-003** 目标仓位架构：每根闭合 bar 计算目标权重，与交易所真实仓位求差后再平衡；`clientOrderId = bd-<bar_open_ms>-<symbol>` 保证同一 bar 幂等。
- **D-004** 最小护栏只保护实验有效性：波动率目标、gross ≤ 2x、单币 ≤ 15%、日亏 −5% 软停、数据过期禁交易、kill-switch 文件、`beidou live flatten`。
- **D-005** `NO_ACTION` 保持上一仓位（不是归零，更不是按 raw score 建仓）。
- **D-006** 循环重启幂等，交易所仓位是唯一真值；允许 launchd KeepAlive + 退避。
- **D-011** 显著性检验对重叠标签做非重叠采样或 Newey-West 修正；随机信号阴性对照必须不显著。
- **D-012** 退出层（`beidou_alpha/overlays/exits.py`）在 bar 收盘评估，阈值以入场时日波动率为单位（止损 / 移动止损 / 止盈 + 冷却期），回测循环与实盘调用同一个 `exit_step`；实盘以交易所的 `entryPrice` 为参考并把状态持久化到 `state.json`。交易所原生条件单明确不做（见 `docs/analysis/2026-09-03-exits-pool-sizing.md`）。
- **D-013** 研究用时点成员表：`beidou data pool history` 用 2021 年以来所有有归档的 USDT 永续的日线成交量按月重建"当时的 top-15"（`--universe pit`），消除幸存者偏差。**两半必须同口径**：研究侧要求 `min_age_days` 根日线才参与排名，实盘 `LivePool.select` 原本完全没有年龄过滤，于是上市九天的新币可以占掉 15 个名额之一、再被 `min_history_bars` 拒绝交易——实盘跑的币数少于为它背书的每一次回测，且无处可见（2026-09-04 修复，`_volume` 顺带返回已收日线根数；pin 也不能绕过，与研究侧一致）。`universe.json` 只有一个写入方：`data pool refresh` 与实盘 sink 走同一条排序规则，`data sync` 只负责下载（此前它按本地 1h 成交额另排一次并写同一个文件，文件含义取决于谁最后跑）。
- **D-014** 实盘每日刷新交易池（同一滞回：进入 ≤15 名、离开 >20 名）；被移出的币目标置 0 并 reduce-only 平仓，直到平掉前仍在受管集合里——**退出侧遍历仓位，进入侧遍历池子**。新进入的币沿用 `min_history_bars` 等待历史。进入侧原本读的是 `leaving`，而 `leaving` 每周期会被过滤成「还有仓位的币」，于是被移出并平掉之后的那一个周期里它仍在 `managed`（该列表在过滤之前就建好了）、模型照常给它权重、没有任何地方归零——实盘会在**已离开池子的币上重新开仓**（复现值 952 USDT）。2026-09-04 修复并加测试；实盘 `cycles.jsonl` 中当时尚无 `left` 记录，因此未曾触发。
- **D-031** 场地健康隔离：某个币在连续 `pool.quarantine_after` 个周期被交易所拒单——且**同一周期内其他币的下单是成功的**——则移出池子并只走 reduce-only 退出，只有下一次每日刷新重新选中它才回来。要求「同周期他币成交」这一条证据，是为了让账户级故障（保证金、时钟、封 IP）永远无法经由这条路清空池子：那属于 guards 的职责。代价是一个盲区：整周期只有一笔单且被拒时不构成对该币的证据，不计数。预登记证伪线：30 天内在没有交易所事故的情况下触发超过两次，说明阈值错了而不是币错了；`beidou report daily` 的 `pool_quarantined` 计数。
- **D-015** 只有一个风险预算（波动率目标 + gross/单币上限）；自适应项只做乘在整本书上的标量（回撤节流）或下单层的约束（保证金、参与率），绝不叠加多个"比例"。
- **D-016** 交易所杠杆 = `min(max_leverage, 档位上限, ceil(max_gross / margin_cap))`（默认 5x），只改变保证金效率，不改变敞口；下单前按可用保证金按比例缩小加仓单。
- **D-017** 退出层与回撤节流的启用由预先登记的验收规则决定（`beidou research overlay`：OOS MDD 改善且 OOS Sharpe 损失 ≤ 0.10），不满足则默认关闭。
- **D-018** 新策略作为独立小书加入（各书独立构建、按 fraction 求和、总书套主书上限）的验收由预登记规则决定（`beidou research book`）；书级 ACCEPT 不替代信号级 PASS。首个用例 flow 空头小书：书级 ACCEPT / 信号级 FAIL；操作者按 D-019 把它作为探针书上线。
- **D-019** 探针书：registry 的 `books:` 声明独立小书（`fraction` = 主书风险预算的比例），策略用 `book` 归属；模型按书独立构建、求和后套主书上限与带（`combine_books`），只有主书时路径逐位不变。`verdict: ACCEPT` 只在非主书且带显式 `probe` 块时被启动检查放行；`beidou_live/probe.py` 按 `attribution.jsonl` 的 30 天归因 P&L 自动停书并持久化，日报在复审日标 REVIEW_DUE。
- **D-020** 验证判定以样本外为主（2026-09-04 操作者决定）：PASS = 走前 OOS Sharpe ≥ 1.0 且 OOS 净收益的 Newey-West t ≥ 2.0，WEAK_PASS = 0.5 / 1.5；折一致性、CPCV 负路径比例、PBO（网格 ≥ 4）、成本 2× 为硬门；DSR 照常报告但不再一票否决（`beidou_alpha/validation/verdict.py`）。
- **D-022** 实盘请求窗口 = `max(profile.history_bars, min_history_bars + 模型在 registry 参数下的 warmup)`（周级 tsmom 为 1,442），超过 1,500 启动即拒绝；`NO_ACTION` 的 hold 以上一周期的 `state.last_contributions` 为种子跨周期持久（D-005 的完整实现），与全历史回测的 forward-fill 同义（E-042）。
- **D-021** 每周期开始先摄入 income：交易性收入按上一周期的贡献归因（份额按 \|贡献\| 归一化）；TRANSFER 类现金流（入金、demo 重置、抵押品兑换）重置日起点与高水位、写入 `cycles.jsonl.external_flows`，日报 drift 跳过该 bar（E-044）。退出层参考价固定为首次入场价，同向加减仓不重锚（E-047）。
- **D-023** 信号自己声明是否消费资金费率历史（`SignalSpec.needs_funding`）；声明为真时 `AlphaModel.targets` 没拿到历史就报错、`LiveEngine.startup` 在行情端口不提供 `funding_history` 时拒绝启动，实盘面板与研究面板由同一份结算费率构成（KILL-027 的结构性关闭）。`beidou live verify`（M-011）用公共数据 + `state.json` 离线重算上一周期的 contributions 并逐币比对；`cycles.jsonl` 的 `gross_before` 改用 `positionRisk` 的仓位求和（账户报文不带 positions 数组时旧口径恒为 0）。
- **D-024** 证据的可复现与可归因：每份 validate 报告记录网格 / 折数 / min_train / purge / 每个配置的全样本 Sharpe，折向量可从报告自身复现（E-049 的教训）；账本按 (param_key, range, symbols) 去重，精确重放只计一次（与 `research book` 一致）；DSR 同时报告 pooled（账本 + 网格离散度）与 noise-null（单个 Sharpe 估计的抽样方差）两个零假设，均为信息性，判定归 D-020；在集成上做决策的报告（`research overlay`）记录 `registry` 指纹——按启用条目经各信号自己的参数对象规范化后的摘要，外加 ensemble 方法与各书 fraction，所以改注释不会变、改参数一定变（P5 那次「证据比结论早过期 15 分钟」靠时间戳才发现）；`research decompose` 把一本书拆成 full / constant_long / sign_only / long_only / short_only / equal_notional，以区分信号与组合构建的贡献（不计入试验账本）。见 `docs/analysis/2026-09-04-round7-strategy-factor-deep-analysis.md`。
- **D-025** 主机时钟是基准（2026-09-04 操作者决定，不校准系统时钟）。因此**恒定的整数个 bar 的偏移是可接受状态而不是故障**：偏移接近整数根 bar 时，循环仍在真实 bar 收盘后不久醒来、交易刚收盘的那根。守的是两件真正有害的事：**对齐误差**（偏移对 interval 取余，决定唤醒时刻是否落在未收盘的 bar 里，超过 `guards.max_bar_alignment_seconds` 告警）与**跳变**（两周期间偏移变化超过半根 bar，会重映射全部标签并可能让 income 水位线倒退——2026-09-04 的 -1023）。`cycles.jsonl.clock` 记录 `skew_ms` / `alignment_ms` / `whole_bars` / `jumped`；日报按 `as_of_ms`（数据自带的 bar）分桶，使一天的报告描述的是真正被交易的那一天。
- **D-026** 构建指纹：`construction_fingerprint` 把组合构建（波动率目标、单币/gross 上限、绝对与相对再平衡带、退出层、回撤节流、杠杆策略、各策略权重）摘要成一个 digest，启动心跳记全量、每周期记 digest。registry 指纹标识*信号*、启动门比对*策略参数*，两者都看不见构建层；2026-09-04 采纳 P10 cell B 时实盘的相对带走到 0.40 而 tsmom 的证据是在 0.25 下验证的，运行记录里没有任何东西说明这一点。它**不拦截**任何配置——构建层与证据分层是否可接受属于操作者决定——只保证一条实盘记录能自我说明。
- **D-028** 判定的第二条件对**选择**敏感（2026-09-04）：PASS 还要求走前 OOS Sharpe ≥ 该策略账本去重后配置数下的期望最大值，零假设取单个 OOS Sharpe 估计的抽样分布而非账本合并离散度（后者两个方向都退化过）。`oos_t_stat` 保留但降格为短样本保护——小时级净收益上它就是 `Sharpe × √年数`（比值 1.001），四年以上不约束。启动门同时比对**组合构建**（`construction_problems`）：无 `portfolio` 段的旧报告跳过，从第一份带该段的报告起，band/半衰期的静默漂移会被拒绝启动。
- **D-030** income 查询窗口用**场地时钟**。签名请求对错误的主机时钟免疫——`-1021` 会让 REST 客户端 resync 再重试，`timestamp` 永远是场地时间——但 `/fapi/v1/income` 的 `startTime`/`endTime` 是普通查询参数，不走那条路径。主机慢 3,612 s 时循环一直在问一个一小时前的窗口：2026-09-04 操作者手动平仓后，96 行、净 +23.98 USDT 停在场地时间 07:51–07:53，而循环在查 `[06:53, 06:58]`，一行也没取到。收入没丢，是**迟到一小时**并被归到一小时之后那一轮的 `last_contributions` 上——这正是 M-010 不能容忍的错位，而 KILL-006 决定不做历史留出的全部理由就是"实盘归因是唯一干净的样本外"。`venue_time_ms()` 读 `-1021` 路径已经在维护的 offset，`startup` 显式同步一次（那里 offset 为 0 不会报错，只会安静地少一小时归因）；水位线不动，因此修完第一轮是一个更宽的窗口把缺口补回来，此后场地基准、首尾相接。没有场地时钟的 venue 回落到主机时钟，时钟抛异常也不会让一轮失败。与 D-025 不冲突：**主机时钟仍是调度基准**，改的只是问交易所要数据时用谁的钟。
- **D-032** 不是本循环下的单，其盈亏不进策略序列。2026-09-04 操作者手动平掉整本书，+26.30 已实现盈亏被归给 tsmom——**经济意义上没错**（仓位是 tsmom 选的、拿的），错的是时间分布：整段持有期的浮盈被压进一根 bar，而 M-010 用逐 bar income 序列算 Sharpe，均值和方差都被带偏。`external_flows` 抓不到它：那只认 TRANSFER 行，人工平仓走的是 REALIZED_PNL。income 行只带 `tradeId` 不带任何来源信息，因此归因走一次 `/fapi/v1/userTrades` 连接：`income.tradeId → userTrades.orderId → trades.jsonl 里本循环自己的委托 id`（该端点接受不带 `symbol` 的时间窗，2026-09-04 实测一小时 68 笔全返回）。外来行进 `foreign` 段——**留在账本里，因为那是真金白银**——但不进 `by_strategy` / `by_symbol` / `total`，日报单列一节。没有 `tradeId` 的行（资金费）留给本书：资金费按持仓计提，与谁开的仓无关，这里分的是"谁交易了"不是"谁在敞口里"。**对账做不了时（端点缺失或调用失败）退回原样全额归因**：一个跑不起来的监控不可以反过来把整轮盈亏静默判给别人。
- **D-033** no-trade band 每条路径只算一层，实盘那一层的参照是交易所的真实仓位。带的规则是「变化不够大就保持原样」，两半系统对「原样」的定义不同：回测里模型自己的输出**就是**仓位，所以 `apply_no_trade_band` 是仓位递推，属于 `build_weights`；实盘里仓位是交易所的，`plan_rebalance` 用同一条规则对着它再判一次——于是模型再算一遍，等于**对着一个不是本书的参照压制了两次**。更糟的是实盘那份递推是在**每周期滑动一根的请求窗口**上从头重建的，锁存点因此是窗口起点的产物：实测同一根 bar，1,442 根 vs 1,443 根让某个币的权重差 9.69e-4（占它自身 14%），200 根 bar 上模型层换手比连续路径高 20%，而证据是在连续路径上测的。`AlphaModel.targets`（实盘唯一入口）现在走 `band=False`，回测路径逐位不变；等价性有测试守着——把未加带的目标逐根喂给 `plan_rebalance`，得到的仓位路径与 `apply_no_trade_band` 逐位相同。修复后同一检验：多给一根 bar 的历史，权重变化 3.0e-9（纯 EWMA 预热残留）。D-026 的构建指纹不变，因为带确实还在跑，只是只剩一层。**这是实盘行为变化，需重启循环才生效。**
- **D-034** 一笔结算属于**包含它的那根 bar**，不属于开盘时刻与它相等的 bar。Binance 的 `fundingTime` 常落在整点后 1–47 ms，且逐年不同（BTCUSDT 2021 年 34% 正好在整点，2024 年 85%）。`funding_per_bar` 与 `Panel.from_frames` 原本按精确时间戳 reindex，于是全库 1,010,914 行结算里 **441,678 行（43.7%）被静默填成 0**：`use_actual_funding: true` 的回测少收了约一半资金费（shipped tsmom book 全样本 Sharpe 1.5809 → **1.5477**，净收益 3.5064 → 3.3575，成本占毛利 10.68% → 12.56%），而且各折丢失比例不同，折间比较本身就不同口径；carry 与 tsmom 的 crowding modifier 则在「看起来完全正常」的情况下只拿到一半输入——这正是 KILL-027 的形状，只是低了一层。现在两处都按 bar 网格 floor 后求和（同一根 bar 内的多笔结算相加），`Panel.from_frames` 还会拒绝非 DatetimeIndex 的 funding 而不是把它填成 0。实盘路径是同一个 bug，此前因 `needs_funding=False` 未触发；旧测试全部用整点合成时间戳，所以谁都没抓到。**后果是操作者决定**：所有引用 `use_actual_funding` 的历史报告数字偏乐观，重跑证据还是逐份标注，不在本次修复范围内。
- **D-035** 风险预算是显式决策，`vol_target` 由它反推（2026-09-04，操作者声明最大回撤 50%）。此前 0.15 是 `PortfolioParams` 的默认值，不在任何决策、预登记或试验账本里，而构造实际跑在约 12% 的预算上——错配约四倍，且会原封不动带进真实资金。取值规则先写后跑：**取自助 q95 回撤仍在声明预算内的最大目标，两个 universe 都要满足** → 0.30（q95 −43.7% 时点 / −49.5% 静态，击穿概率 1.2% / 4.8%）；0.375 两边都否决。**样本内回撤不是用来定档的数**：0.15 时它读 −11.9%，而自助中位数 −16.5%，历史值落在自己分布的约第 25 百分位。这个旋钮在回测里**不含 alpha**，而且那是算术性质不是发现——毛盈亏、换手成本、资金费三项全部线性于权重，所以任意缩放后净 Sharpe 精确不变（时点 1.6972 / 静态 1.5760，每一个 k）。**因此它只在 demo 名义下成立**：成本模型对任何下单量都收固定 7 bps，`max_participation` 根本不在回测里，真实资金前必须在含冲击的成本模型下重新推导。预登记降档阶梯（`risk_budget:` 块，`beidou_live/risk_budget.py` 每小时经 `report daily --check` 度量）：回撤 −35% → 0.225，−50% → 0.15；实现波动出 26–38% 带、滑点 > 10 bps 同样告警。**它只告警不交易**：「自动、不进入复审」指的是阈值不再商量，而不是让 cron 去改实盘仓位大小。算不出的指标一律返回 `enforced: false` 加原因，绝不读成 0。
- **D-036** 书级护栏只有一份语义，回测重放实盘真正会做的事。`daily_loss_pause` 与 `GROSS_CAPPED` 从来不在回测里，而这在 `vol_target 0.15` 下**看不出来**：5.6 年最差 UTC 日 −3.5%，gross 从未越过 2.0，两者都不可达。0.30 让它们都可达（时点 355 个 capped bar、36 个 paused bar），不补就是在给一本实盘不会持有的书打分——KILL-027 的形状。语义因此下沉到 `beidou_alpha/overlays/exposure.py`（`clamp_book` / `hold_or_reduce`），`beidou_live/guards.py` 调同一份，`run_backtest(..., guards=)` 做因果重放：日界滚在**决策 bar** 而不是执行 bar（实盘 `_roll_day(bar_open_ms)` 如此，小时级下两者每天跨一次 UTC 午夜），且**不能向量化**，因为暂停读的是它自己正在产生的权益路径。验收是恒等性：0.15 下重放与既有权重逐位一致、护栏触发 0 次；0.30 下 OOS Sharpe 反而 +0.005。同时补上 D-026 自己漏的一半——`LiveConfig` 此前不携带 `vol_target`，改书的大小不会改变构造 digest。
- **D-037** 交易所每标的杠杆不参与本书的收益与风险，「自适应杠杆」明确**不做**；`margin_cap` 改为启动时校验的不变量。仓位由 `weight × equity` 决定；`maintMarginRatio` 按**名义档位**索引（BTCUSDT 首档 `notionalFloor 0 / cap 50000 / MMR 0.004`），与所选杠杆无关，全仓强平由维持保证金决定；L≥3 时可用保证金对 gross ≤ 2.0 从不绑定。三条合起来意味着它没有可优化的目标函数——而 legacy 的同一模块（八个标量相乘、从未验证、交易所杠杆停在 20x）正是审计判为不可移植的那个。真实缺陷在别处：`derive_leverage` 按最坏情况取值是**正确设计**（按实际 gross 推导会推出 L=1 并锁死整本书），但 `max_leverage` 的截断会静默破坏 `margin_cap`——`max_gross 3.0 / cap 0.40 / max 5` 实得 5x、初始保证金 60%、无告警。今天不可达只因 `2.0 = 5 × 0.40` 恰好相等，而 P13 把保证金峰值从 33% 推到 40%，余量归零。`auto` 模式下启动即校验并拒绝；`fixed` 豁免，因为那里 `margin_cap` 根本不参与（profile 自己的「was 100% at a fixed 2x」就是那个状态）。
