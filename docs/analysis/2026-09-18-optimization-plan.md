## 4. 推荐排序，以及它的理由

**推荐：G-C → G-B → G-A → G-D。** 这是建议不是结论；B1 是操作者的决定。

1. **G-C（吞吐）排第一**，因为它是唯一在**冻结期内**可推进的，而且它是乘数——其余三个目标都受限于
   「你一年能诚实评估多少个假设」。桶 A 全部属于它，价钱全零。

2. **G-B（回撤）排第二**，因为它的四项（C2–C5）**已经预登记完毕**，10-13 当天可以直接跑，不需要新的
   设计工作。它与 G-A 的冲突是本方案唯一有实例的那一格，先做 G-B 意味着在 D-018 这道门上先有独立
   推导（C5），再让 G-A 的候选去撞它。

3. **G-A（Sharpe）排第三**，因为它花的是最稀缺的资源（52 笔），命中率最低（真 Sharpe 1.5 在 N=299
   下过门概率 **43.3%**，且这是不含 CPCV / PBO / fold 一致 / 成本 ×2 的**上界**），而且——

   **C1 有一个被低估的价钱。** `beidou_live/construction.py:76` **[本文实测]**：M-010 的 30 天窗口
   「自 2026-09-04T15:02Z 起未断过」。加一个 sleeve 会**清零它**。所以 C1 的真实价钱不是「一个 probe
   名额」，是**再等 30 天**——而 M-010 正是冻结期本身要攒的那个东西。把 C1 排在 M-010 交付之后，它的
   价钱从「30 天」降到「0」。这条理由在上一份文档的 §13 里写弱了，本文更正。

4. **G-D（真实资金）排第四**，因为这是操作者自己的排序：Q3 答「再观察数月后再定」。它的四项里有两项
   （D2、D3）在拿到真实成交之前根本校准不了，所以早做也换不来把握。

**这个排序会伤到谁**：如果 G-A 排第三，tsmom 主书的 52 笔 headroom 在 10-13 前不会被动——这对主书是
好事。真正的受损方是 **residual**：C1 推后意味着它继续在前向板上等 3.48 年，而一个 probe 名额本可以
在 30 天内给出实盘读数。**补偿**：如果 M-010 在 10-13 前交付，C1 的 30 天代价归零，两者不再冲突。

### 9.2 B2 · pit 成员表重建 —— 已执行

**执行前发现根因不是成员表，是它依据的数据。** 核 `.beidou/data/klines/*/1d.parquet`
**[本文实测]**：877 个有 1d 的标的里 **847 个末根日线是 2026-09-03**，包括 BTCUSDT / ETHUSDT /
SOLUSDT 这些当前在池成员——它们的 1h 是 2026-09-17，1d 是 2026-09-03。

**为什么会这样，以及它不是缺陷**：每天 01:20 的 `com.beidou.data`（`deploy/run_data.sh`）跑的是
`data sync` + `data spot` + `data pool refresh`。`data sync` 的 docstring 写着它只管
「universe candidates 的 klines + funding」，**不写 1d**；`data pool refresh` 刷的是 `universe.json`
这份实盘名单，**不碰 membership**。1d 只由 `data pool history --sync` 写——而它上次运行正是
**2026-09-03**。所以「成员表停在 09-03」与「日线停在 09-03」是同一个事实的两种说法，不是两个问题。

**并发核过再动手**（RISK-LD05）：三个 live 进程在跑（armed PID 88298、paper 811、shadow 83947），
都只读 1d；无其他 worktree；`com.beidou.data` 在 01:20 不在现在。执行窗口选在整点后 5 分之后。

`sync_daily`（`beidou_data/pool.py:55-67`）是**增量**的：读 store 末根，listed 走 REST 只取缺的那一段，
delisted 走归档只取缺的那几个月。实测 **1 标的/秒**，890 个候选，**12 分钟**，1 个错误
（GAIBUSDT，退市标的的 REST 400——与 #27 回填遇到的是同一类）。日线随之由 09-03 推到 **09-17**，
851 个标的当前。

**为什么它贵**：`config/alpha_registry.yaml` 记着逐日口径是**特意换上去**的——逐月带着
「survivorship-adjacent bias」，值 **0.07 OOS Sharpe**，而 `RESEARCH_LOG.md:638` 把两种口径的读数
逐位记了下来（逐月 69 次刷新 / 146 币 / 6.68 次变更每月；逐日 2,042 / 211 / 0.36）。**我弄坏的那版
与「逐月」那一列逐位相同**，这既是确诊也是证据。

**怎么发现的**：核重建结果时行数从 2,042 掉到 69。我在 `--help` 的输出里读到过 `[default: MS]`，
没有当回事——正是校准表里那条「**默认值 = 贵的那个**」的旗标。

**修复**：`data pool history --refresh D --no-sync`（日线已新鲜，不必再走网络），16 秒。
**交叉核对**：新表的 `0.36 changes/refresh` 与 `RESEARCH_LOG.md:638` 记录的逐日口径**逐位相同**。

#### 一条本文之前定价过低的后果

### 9.4 核并发时撞见的两条系统事实

都不是本方案的范围，但都可观察、都该有人知道，所以记在这里而不是丢掉。

**(1) `com.beidou.check` 每小时退出码 1，不是任务坏了。** 它每小时第 10 分跑
`deploy/run_check.sh`，链条里 `status / verify / plists / soak` 全部 `ok`，只有 `report` 一步报 FAIL，
而 FAIL 的内容是日报里的两条 **advisory**：

> 最近 7 天有 2 次构造变更；计划允许每周一次晋升
> 风险预算告警：滑点（主书）4.7 bps 高于假设的 4 bps（±2.4，与噪声不可分辨）

脚本把 advisory 当失败，所以只要这两条不消，`launchctl list` 里 `com.beidou.check` 就一直是 1。
**两条 advisory 本身是真信号**：第二条直接落在 G-D（滑点假设与实测的差距），与
`config/costs.yaml` 里那段「4.43 bps 实测、`slippage_bps` 仍是 2.0」的记录同向。

**(2) 1d 与 1h 的刷新责任分属两条不同的路径**，见 §9.2。它的后果是：任何**不传 `--universe pit`**
的研究运行读到的默认总体、以及任何依赖 1d 的分析（上市日期、日频事件研究），都会静默地停在上一次
`pool history` 跑过的那天。这不是缺陷，是分工；但它没有写在任何一处文档里，**现在写在这里**。
